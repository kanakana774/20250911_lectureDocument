# 排他制御と ACID 特性に関する整理（RDBMS・EC サイト事例）

## 1. 排他制御の全体像

RDBMS では、**更新時に自動的に行ロックを取得**するため、  
基本的な「他トランザクションとの同時更新の衝突」は DB レベルで防止される。  
アプリケーション層で明示的に排他制御を行うのは、主に以下のような場合である。

### 1.1 RDBMS レベルの排他

| 操作            | PostgreSQL の挙動                             | 説明                                                   |
| --------------- | --------------------------------------------- | ------------------------------------------------------ |
| SELECT          | ロックなし（MVCC によるスナップショット読み） | 読み取り専用。更新中の行はコミット済みの最新値のみ参照 |
| UPDATE / DELETE | 対象行に行ロック（Row Lock）                  | 他 Tx の同一行更新をブロックし、順次実行される         |
| INSERT          | 同一 PK や一意制約との競合時のみブロック      | 独立行は即座に挿入可能                                 |

---

### 1.2 アプリケーション層での排他が必要なケース

| 条件                             | 説明                                                 |
| -------------------------------- | ---------------------------------------------------- |
| 参照から更新までの間隔が存在する | 画面表示 → ユーザー操作 → 更新など、時間差がある場合 |
| 更新内容が参照時の状態に依存する | 参照内容に追記・部分更新する場合（メモ欄追記など）   |
| 競合を論理的に検出・通知したい   | 他ユーザーの同時編集を検出して通知する場合           |

---

### 1.3 アプリ層の排他が不要なケース

| 条件                                  | 説明                               |
| ------------------------------------- | ---------------------------------- |
| 更新内容が参照状態に依存しない        | 在庫数の減算、固定値更新など       |
| 参照から更新までが短い                | 1 トランザクション内で完結する処理 |
| DB の行ロックで十分に排他が保証される | 一般的な在庫・残高更新など         |

---

## 2. 在庫更新の実務的アプローチ

### 2.1 UPDATE 条件付きで在庫チェック（シンプル・確実）

```sql
UPDATE product
SET stock = stock - :quantity
WHERE id = :productId
  AND stock >= :quantity;
```

- UPDATE 実行時に行ロックが自動取得
- 在庫不足時は更新件数 0 → アプリで「在庫切れ」と判断
- CHECK 制約でマイナス禁止を補強可能
- 明示的な `SELECT FOR UPDATE` は不要

### 2.2 予約モデル（長時間決済向け）

1. 決済前に在庫を予約（reserved +1）
2. 決済完了時に在庫減算・予約減算
3. 決済失敗時は予約解除

- 外部 API 呼び出しの長時間処理でもオーバーセル防止可能
- 大規模 EC サイトで多く採用

### 2.3 悲観ロックで厳密排他（少量競合向け）

```java
@Transactional
public void buyProduct(Long productId) {
    Product p = productRepository.findByIdForUpdate(productId); // SELECT ... FOR UPDATE
    if (p.getStock() <= 0) throw new SoldOutException();
    p.decreaseStock(1);
    productRepository.save(p);
}
```

- ロック中に外部 API 呼び出しはスループット低下のリスクあり
- 「絶対に二重販売不可」な商品で有効

---

## 3. @Transactional とロックの関係

- `@Transactional` メソッド内の UPDATE は **行ロックを取得**
- 行ロックは **メソッドの処理が完了するまで（commit まで）保持**
- ロックは「対象行単位」で取得されるため、テーブル全体は影響なし
- 実務では、トランザクションは短く設計するのが原則

  - 外部 I/O（決済 API など）を含めない
  - 必要最小限の処理のみトランザクションに含める

---

## 4. ACID 特性と排他制御

| 特性                         | 説明                                                     | 実務例（EC サイト購入）                                             |
| ---------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------- |
| **A: Atomicity（原子性）**   | トランザクション内の全操作は全て成功するか全て失敗するか | 在庫減算 + 注文登録 + 決済 API 呼び出し。決済失敗なら在庫も元に戻る |
| **C: Consistency（一貫性）** | トランザクション前後で整合性が保たれる                   | 在庫数がマイナスにならない、注文テーブルの外部キー制約を満たす      |
| **I: Isolation（独立性）**   | 同時実行トランザクション間で未コミット変更が見えない     | 2 人が同時購入しても、行ロック＋ MVCC で整合性保持                  |
| **D: Durability（永続性）**  | コミット後の結果は障害が起きても保持される               | WAL に書き込み済み → サーバクラッシュ後も在庫・注文情報は復元可能   |

- **Isolation** は排他制御（行ロック・MVCC）によって実現
- **Atomicity** はトランザクション全体のロールバックで保証
- **Consistency** は DB 制約や条件付き UPDATE で補強
- **Durability** は WAL やログ再生で保証

---

## 5. まとめ

- RDBMS の行ロックと MVCC により、基本的な同時更新の衝突は防止される
- アプリ層での明示的排他（version 列など）は、参照 → 更新間の論理的整合性やユーザー通知が目的
- 在庫更新のような即時確定型処理では、**条件付き UPDATE + トランザクション短時間化**で十分安全
- ACID 特性は排他制御の背景として理解することで、設計上の意図を明確化できる

## 🔹1. 前提：楽観ロックの目的

楽観ロックの目的は「**同じデータを同時に操作した複数トランザクションによる“上書き事故”を防ぐ**」ことです。

- 排他ロック（悲観ロック）＝他の人が触れないようにする（物理的な防止）
- 楽観ロック ＝同時変更が起きたら後から気づいて弾く（論理的な防止）

---

## 🔹2. CRUD 操作と競合の構造

| 操作       | 他トランザクションと競合しうる点                                     | ロック                        | 楽観ロックの関与            |
| ---------- | -------------------------------------------------------------------- | ----------------------------- | --------------------------- |
| **SELECT** | 更新・削除と競合（更新中は読めるが、更新直後は古いスナップショット） | 共有ロックなし（MVCC で回避） | ✖ 不要                      |
| **INSERT** | 主キー重複時に競合                                                   | 行レベル排他ロック            | ✖ 不要（PK 違えば別行）     |
| **UPDATE** | 同一行を他 Tx が更新していたら競合                                   | 行ロック（`FOR UPDATE`相当）  | ⚪ 有効（上書き検出）       |
| **DELETE** | 同一行を他 Tx が更新/削除していたら競合                              | 行ロック                      | ⚪ 有効（削除対象の整合性） |

---

## 🔹3. MVCC と Read Committed 前提の挙動

あなたの指定通り「READ COMMITTED」で固定すると：

- SELECT は「**コミット済みの最新バージョン**」のみを読む
  → 他 Tx の未コミット更新は見えない
- UPDATE は更新時に対象行の**最新バージョンを再確認**する
  → 他 Tx が先に更新してコミットしていたら、実質的に**更新失敗（競合）**

この「再確認」のとき、PostgreSQL 自体が内部的に**行ロックとバージョン比較（xmin/xmax）**をしているため、
実務上は「楽観ロックがなくても、古いスナップショットを基にした更新は失敗」します。

---

## 🔹4. それでも楽観ロック（version 列）が有効なケース

### ✅ 1. アプリケーションで「更新競合を明示的に検出・通知したい」場合

たとえば：

```java
UPDATE product
SET price = :newPrice, version = version + 1
WHERE id = :id AND version = :version
```

→ 更新件数が 0 なら「他のユーザーが先に更新済み」と判断できる。

つまり、**DB 内部ではなくアプリ側で“意図的に”整合性エラーを扱いたい場合**に意味がある。

---

### ✅ 2. 「部分更新」ではなく「状態更新」のケース

例：

- 商品のステータス（`status` = '在庫あり' → '売り切れ'）
- ユーザーのステータス（`active` → `deleted`）

このように「前提状態が変わっていたら処理をやめたい」場合、
楽観ロックで「処理前の状態」を条件に含めるのが合理的。

---

### ✖ 不要なケース（あなたの指摘通り）

- 更新内容が「現在の値に依存しない」ケース
  例：

  - `在庫数 = 10` → `在庫数 = 5`（固定値設定）
  - `最終更新日 = now()`
    これらは「前の値を参照しない」ため、version チェックで弾いても意味が薄い。

この場合は **DB の行ロックで十分**。
競合時にはトランザクション再試行で済む話です。

---

## 🔹5. 結論まとめ

| 観点                                             | 楽観ロックの意義         |
| ------------------------------------------------ | ------------------------ |
| **更新が前の状態に依存する**                     | 意義あり（上書き検出）   |
| **更新内容が独立している**                       | 意義薄い（ロックで十分） |
| **アプリ側でユーザーに「更新競合」を通知したい** | 意義あり                 |
| **在庫更新のような排他が本質的に必要な業務**     | 悲観ロックの方が適切     |

## 🔹6. 現場での運用バランス

実務では以下のような棲み分けが多いです。

| ケース                            | 採用ロック方式                    |
| --------------------------------- | --------------------------------- |
| 通常の更新                        | MVCC + 行ロック（DB 任せ）        |
| 重要な整合性（2 人が同時編集）    | 楽観ロック（version 列）          |
| 数量系（在庫・残高）              | 悲観ロック（`SELECT FOR UPDATE`） |
| 履歴や一時保存付き UI（編集画面） | 楽観ロック（version 列）          |

## 🔹1. 前提：在庫更新の性質

在庫更新は「**競合が発生しうるが、処理時間が短いトランザクション**」です。
だから、悲観ロックを取っても実害が少ない。

- 更新単位：商品単位（1 行〜数行）
- トランザクション時間：数ミリ秒〜数百ミリ秒
- 同時更新確率：人気商品以外は低い
- 更新内容：「現在の数量 - 購入数」など、**現在値に依存する更新**

→ よって、**DB レベルの行ロック（悲観ロック）で十分安全かつ高速**。

---

## 🔹2. 実際の在庫更新ロジック例（PostgreSQL 想定）

### ✅ パターン A：安全・シンプルな悲観ロック方式

```sql
BEGIN;

-- 在庫をロックして読み取る
SELECT stock
FROM product
WHERE id = :productId
FOR UPDATE;

-- 在庫チェック
IF stock >= :quantity THEN
  UPDATE product
  SET stock = stock - :quantity
  WHERE id = :productId;
ELSE
  ROLLBACK;
  RAISE '在庫不足';
END IF;

COMMIT;
```

- `FOR UPDATE` が **行ロック**を取る（他 Tx の同一商品の更新をブロック）
- 更新完了後にロック解除
- ユーザーが商品ページを閲覧中でも問題なし
  → ロックされるのは「購入確定ボタン押下時のみ」

つまり：

> 📦「ユーザーが商品ページを“見ている”間はロックしない」
> 💳「“購入処理”で在庫行にロックを取る」

という設計です。

## 🔹3. なぜ楽観ロックを使わないか？

あなたの指摘どおり、在庫更新は**前の値を参照して加減算する処理**なので、
楽観ロック（version 列）のように「前の状態と一致していないと更新拒否」する意味がほぼありません。

なぜなら、次のような SQL を書けば自動的に競合を解決できるからです 👇

```sql
UPDATE product
SET stock = stock - :quantity
WHERE id = :productId
AND stock >= :quantity;
```

- 1 トランザクションが完了するまで、PostgreSQL が行ロックを保持
- 他の Tx は更新完了を待つだけ
- 更新件数が 0 なら「在庫不足」と判定できる
  → アプリで「在庫切れ」メッセージを出すだけで十分

→ version 列を使っても実質的に同じ結果なので、**DB の MVCC + 行ロックで十分安全**。

## 🔹4. 競合検出をしたい場合のみ「楽観ロック＋再試行」

例えば「在庫管理者が複数人同時に手動調整する」など、
人間操作で“編集画面を長時間開く”パターンでは、version 列を使うことがあります。

例：

```sql
UPDATE product
SET stock = :newStock, version = version + 1
WHERE id = :id AND version = :version
```

- 更新件数 0 → 誰かが別の値で更新したと判断
- 管理画面で「他の人が更新しました。再読み込みしてください」と表示

→ このように、「**ユーザー編集競合の検出**」目的でのみ有効。

| 商品ページ閲覧         | ロックなし                         | SELECT のみ（MVCC）        |

| 管理画面編集           | 楽観ロック                         | 編集競合の明示通知が必要   |

## 🔹 排他制御の全体像

RDBMS では、**更新時に自動的にロックを取得する**ため、
基本的な「他トランザクションとの同時更新の衝突」はデータベースレベルで防止されている。
このため、通常の CRUD 操作においては DB が提供する排他制御（行ロックや MVCC）で十分である。

---

## 🔹RDBMS が自動で行う排他（標準的な制御）

| 操作            | PostgreSQL での排他制御                       | 説明                                                             |
| --------------- | --------------------------------------------- | ---------------------------------------------------------------- |
| SELECT          | ロックなし（MVCC によるスナップショット読み） | 読み取り専用。更新中の行はコミット済みの最新バージョンのみ参照。 |
| UPDATE / DELETE | 対象行に**行ロック（Row Lock）**              | 他 Tx の同一行更新をブロックし、順次実行される。                 |
| INSERT          | 同一 PK や一意制約との競合時のみブロック      | 通常は独立した行として挿入可能。                                 |

このため、更新系トランザクション間の「同時書き込み衝突」は DB が自動的に防ぐ。

---

## 🔹 アプリケーション層で明示的に排他を考慮すべきケース

DB のロック機能では防げない領域において、アプリケーション側での排他制御（＝楽観ロックなど）を導入する意味がある。
代表的な条件は以下のとおり。

| 条件                                   | 説明                                                                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **① 参照から更新までの間隔が存在する** | 画面表示 → ユーザー操作 → 更新、のように**人間操作**を伴う場合。参照時点の状態が更新時には変化している可能性がある。           |
| **② 更新内容が参照時の状態に依存する** | 「参照した内容に追記・変更を加える」タイプの処理。例：自由記述メモの追記、設定のオンオフ切替、複数人で同一レコードを編集など。 |
| **③ 競合を論理的に検出・通知したい**   | DB レベルでは検知できない「同じレコードを別ユーザーが同時に変更した」ことをアプリ側で明示的に検出し、ユーザーに伝えたい場合。  |

---

## 🔹 逆に、アプリ側での排他（楽観ロック等）が不要なケース

| 条件                                                   | 説明                                                                                         |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| **① 更新内容が参照状態に依存しない**                   | 例：在庫数を「現在値から減算する」「固定値に更新する」など、更新時点で一貫して決定できる値。 |
| **② 参照から更新までが短い（同一トランザクション内）** | バッチ処理や自動更新ジョブのように、1 トランザクション内で読み → 更新が完結する場合。        |
| **③ DB の行ロックで十分に排他が保証される**            | 在庫・残高更新のように DB が行レベルで確実に整合性を担保できるケース。                       |

---

## 🔹 整理すると

> RDBMS の排他制御は「**更新の同時実行**」を防ぐ。
> アプリケーションの排他制御は「**論理的な矛盾**」を防ぐ。

---

## 🔹 具体的な使い分け例

| シナリオ                 | 排他制御方式                | 理由                                      |
| ------------------------ | --------------------------- | ----------------------------------------- |
| 在庫数の更新（購入確定） | DB の行ロック（悲観ロック） | 短時間処理・数値加算。DB 排他で十分。     |
| 管理画面での商品情報編集 | 楽観ロック（version 列）    | 編集画面での参照 → 更新間に時間差がある。 |
| 定期バッチでの在庫調整   | 行ロック or SERIALIZABLE    | トランザクション一貫性重視。              |
| メモ欄や設定値の追記     | 楽観ロック                  | 参照状態を元にした部分更新。              |

## 🔹 まとめの一文（定義的表現）

> RDBMS は更新の物理的な排他を保証するが、
> アプリケーションで明示的な排他を導入するのは、
> 「参照時点の状態を前提に更新を行う」場面、すなわち**論理的整合性を守るため**である。

---

このように整理すると、「DB が守る排他」と「アプリが守る排他（version 列など）」が**“責務のレイヤー”として明確に分離**できます。

## 🔹 結論から言うと

> 「在庫更新時の悲観ロック」とは、**アプリ側で明示的に `SELECT ... FOR UPDATE` すること**を指しているのではなく、
> **`UPDATE` が自動的に取得する行ロック（PostgreSQL 内部の悲観ロック）**のことを指しています。

あなたが言う通り、**更新前の `SELECT FOR UPDATE` は不要**です。
正しく書けば `UPDATE` 一発で十分です。

## 🔹 実際の在庫更新の安全な書き方

例えばこんな SQL が現場でよく使われます 👇

```sql
UPDATE product
SET stock = stock - :quantity
WHERE id = :productId
  AND stock >= :quantity;
```

これだけで次の 3 つが同時に実現されます：

1. **在庫数がマイナスにならないように条件付き更新**
2. **`UPDATE` 時点で行ロック（排他）を自動取得**
3. **在庫不足時は更新件数 0 → アプリ側で検出可能**

つまり、これ 1 文で**悲観ロック＋整合性検査＋競合検知**が完結します。
（あなたが仰る通り、CHECK 制約でマイナス禁止を補強しておくのも有効です）

---

## 🔹 なぜこれで安全なのか（内部動作）

- `UPDATE` が実行されると、対象行に対して PostgreSQL は **Row Exclusive Lock** を取得します。
- そのロックはトランザクション完了（COMMIT / ROLLBACK）まで保持され、他トランザクションの同一行更新を待機状態にします。
- したがって、同じ商品を別ユーザーが同時に購入しても：

  - 先にロックを取ったトランザクションが在庫を減算し、コミット。
  - 後のトランザクションは更新件数 0（在庫不足または条件不一致）で終了。

→ アプリ側では「売り切れ」として扱えば良い。

## 🔹 つまり整理すると

| 観点                                         | 内容                                                                                                              |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **悲観ロック**                               | RDBMS が `UPDATE` 実行時に自動的に取得する行ロックのこと。アプリが `SELECT FOR UPDATE` で明示的に取る場合も含む。 |
| **明示的な悲観ロック (`SELECT FOR UPDATE`)** | 「先に読み取ってから判断して更新したい」場合に限定して使う。通常の在庫減算では不要。                              |
| **在庫減算の安全策**                         | `UPDATE ... WHERE stock >= ?` + `CHECK(stock >= 0)` + トランザクション境界。                                      |
| **楽観ロック**                               | 在庫数のような定量値更新には不要。論理的編集競合を扱いたい場面で使う。                                            |

| パターン            | SQL                                                     | 排他方法                    | 主な用途                             |
| ------------------- | ------------------------------------------------------- | --------------------------- | ------------------------------------ |
| A. 即時減算         | `UPDATE product SET stock = stock - ? WHERE stock >= ?` | DB 行ロック                 | 決済確定時などリアルタイム更新       |
| B. 仮在庫確保       | `INSERT INTO reserved_stock ...`                        | 一意制約                    | カートや予約保持のための中間テーブル |
| C. 確定時に在庫反映 | A+B の組合せ                                            | DB 行ロック＋整合性チェック | 大規模 EC の一般構成                 |

### ✅ 結論（きれいに一文でまとめると）

> 在庫更新のような即時確定型の更新処理では、
> `UPDATE` 文が自動的に取得する行ロック（RDBMS レベルの悲観ロック）で十分。
> 明示的な `SELECT FOR UPDATE` は不要であり、
> 条件付き `UPDATE` と整合性制約で安全かつ効率的に排他制御できる。

## 🧩 1. @Transactional の動作とロックの寿命

Spring の `@Transactional` は、メソッドの開始時にトランザクションを開始し、
正常終了時に `commit`、例外で `rollback` します。

```java
@Transactional
public void updateStock(Long productId, int count) {
    Product p = productRepository.findById(productId);
    p.decreaseStock(count);
    productRepository.save(p);
}
```

このとき、JPA や MyBatis の内部では次のようになります。

| 処理                   | PostgreSQL 側の挙動                    |
| ---------------------- | -------------------------------------- |
| `findById`             | SELECT（行ロックなし）                 |
| `save` → UPDATE 文     | **対象行に行ロック（Row Lock）を取得** |
| `commit` or `rollback` | ロック解放                             |

つまり、**UPDATE 文の発行時点でロックが取られ、commit するまで保持されます。**

---

## ⚙️ 2. ロックは「必要最小限」なので大きなオーバーヘッドにはならない

行ロックは、**該当する行のみ**に対してかかります。
つまり、同じテーブルの他の行には同時にアクセスできます。

例：

| product_id | stock | トランザクション | ロック状態       |
| ---------- | ----- | ---------------- | ---------------- |
| 1          | 10    | TX1 が UPDATE 中 | 🔒（ロック中）   |
| 2          | 5     | TX2 が UPDATE 中 | 🔒（別のロック） |
| 3          | 0     | 空き             | 🟢               |

このように、**スケールしやすいのは PostgreSQL の MVCC の強み**です。
テーブル全体やページ単位でロックを取るわけではないので、
ほとんどの EC サイト・業務システムではこのレベルで十分。

---

## 🧠 3. 実務ではトランザクションは短く設計するのが鉄則

ただし注意点として、
`@Transactional`メソッドが「時間のかかる処理」を含むと、
その間ロックを保持してしまいます。

### 悪い例（ロック保持が長い）

```java
@Transactional
public void buyProduct(Long productId) {
    Product p = productRepository.findById(productId);
    Thread.sleep(5000); // 決済API呼び出しなど
    p.decreaseStock(1);
    productRepository.save(p);
}
```

→ この場合、**5 秒間ロックが保持される**ため、他トランザクションが待機します。

### よい例（トランザクション短縮）

```java
public void buyProduct(Long productId) {
    // 決済前に在庫確認（トランザクション外）
    Product p = productRepository.findById(productId);
    if (p.getStock() <= 0) throw new SoldOutException();

    // 決済処理（トランザクション外）
    paymentService.pay(...);

    // 在庫確定のみトランザクションで実行
    productService.decreaseStock(productId, 1);
}

@Transactional
public void decreaseStock(Long productId, int count) {
    productRepository.decreaseStock(productId, count); // UPDATE
}
```

→ このように、**実際に更新する瞬間だけトランザクションを張る**のがベストプラクティスです。

## 🧩 状況整理

上記の例では、

1. トランザクション外で在庫を確認 (`SELECT stock FROM product WHERE id = ?`)
2. 決済処理（時間がかかる）
3. 決済完了後に在庫を更新 (`UPDATE product SET stock = stock - 1 WHERE id = ?`)

という流れです。

この間に、別のトランザクション（別の購入者）が同じ商品を買ってしまう可能性があります。

結果的に、複数人が同じ在庫を奪い合う形になり、在庫数がマイナスになるか、
在庫チェック後に更新失敗（0 件更新）となる可能性があります。

---

## ⚙️ どう設計すべきか（実務的な 3 パターン）

### ✅ パターン ①：UPDATE 条件で在庫をチェック（シンプル・確実）

在庫更新時に **条件付き UPDATE** にします。

```java
@Transactional
public boolean decreaseStock(Long productId, int count) {
    int updated = jdbcTemplate.update("""
        UPDATE product
           SET stock = stock - ?
         WHERE id = ?
           AND stock >= ?
    """, count, productId, count);
    return updated > 0;
}
```

→ 更新件数が 0 なら「在庫なし」と判断してロールバック。
この方法なら、**トランザクションを短く保ちつつ整合性も保てる**ため、実務で最もよく使われます。
`SELECT FOR UPDATE` は不要。

---

### ✅ パターン ②：在庫テーブルを別トランザクションで予約する（予約ロジック導入）

EC サイトのように**決済が長い**処理を伴う場合は、
「決済前に在庫を確保」→「確保した在庫を後で確定または解放」
という 2 段階構成にするケースがあります。

例：

1. 購入ボタン押下時：`UPDATE product SET reserved = reserved + 1 WHERE stock - reserved > 0`
2. 決済完了時：`UPDATE product SET stock = stock - 1, reserved = reserved - 1`
3. 決済失敗時：`UPDATE product SET reserved = reserved - 1`

→ Amazon などの大規模サイトでよくある「在庫確保モデル」です。
トランザクションの寿命を短く保ちつつ、オーバーセルも防止できます。

---

### ✅ パターン ③：悲観ロックで確実に制御（少量トラフィック向け）

もしその商品が「数量限定」「1 個限定」など競合が非常に少ない場合は、
敢えて悲観ロックで確実に排他することもあります。

```java
@Transactional
public void buyProduct(Long productId) {
    Product p = productRepository.findByIdForUpdate(productId); // SELECT ... FOR UPDATE
    if (p.getStock() <= 0) throw new SoldOutException();

    paymentService.pay(...); // ここは別の外部サービス呼び出しは避けるか工夫
    p.decreaseStock(1);
    productRepository.save(p);
}
```

→ ロック中に外部 API 呼び出しがあるとスループットは落ちますが、
業務上「絶対に二重販売できない」商品ならこちらが安全です。

| ----------------------------- | ------ | -------------- | ---------------------- |
| UPDATE 条件付き（パターン ①） | ◎      | ◎              | 一般的な EC・在庫管理  |
| 予約モデル（パターン ②）      | ◎      | ○              | 大規模 EC・長時間決済  |
